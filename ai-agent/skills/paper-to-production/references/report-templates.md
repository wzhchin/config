# 产出物模板

Step 5 直接套用的三份模板。模板是骨架，**具体场景具体分析**——填不上的地方写"需补充 XX"或"需 PoC 验证"，不要硬编。

## feasibility-report.md（落地评估）

```markdown
# {论文} 落地 {场景} 可行性评估

## 一、方法内核
这篇论文真正的新东西是什么（一句话，去实验装饰）。
论文在什么数据集 / 规模 / 指标下证明了有效 → 这界定了它的已知适用边界。

## 二、场景契合度
论文解决的问题 vs 场景的核心痛点：是否对齐。
输入输出契约能否对上。

## 三、收益评估
比现有/简单基线好多少？好的部分值不值这个成本。
{如果可量化：给出预估提升区间，标注 [预估] 和依据}
{如果不可量化：定性说明收益类型——效果/效率/覆盖/体验}

## 四、成本评估
- 算力：训练 {预估} / 推理单次 {预估}
- 人力：{维护成本，团队熟悉度}
- 基础设施：{需要新增什么}
标注 [预估] / [需实测]。

## 五、关键风险（按严重度排序）
| 风险 | 严重度 | 概率 | 缓解措施 |
|------|--------|------|----------|
| ...  | 高/中/低 | 高/中/低 | ... |

## 六、结论与建议
✅/⚠️/❌ + 理由 + 下一步动作。
若 ⚠️：明确 PoC 要回答的关键问题 + 成功标准（怎样算 PoC 通过）。
```

## 写作纪律（适用于全部三份）

- **数字带单位带条件**："50ms" → "p99 50ms @ 1000 QPS，单卡 A10"
- **预估必标注**：`[预估·依据: 同类方法经验值]` 或 `[需实测]`
- **场景信息不足时不硬填**：写"需补充 {具体信息} 才能判断"，并把该维度标为待确认
- **选型给理由**：每个技术选型都关联到用户的具体约束，不堆砌流行框架名
- **结论可证伪**：判断要能让用户拿着去反驳，不要写永远正确的废话
